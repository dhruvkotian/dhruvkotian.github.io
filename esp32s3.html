ACM TECS · MANUSCRIPT UNDER REVIEW

Bytes, not FLOPs.

An int8 KV cache and 128-bit PIE attention let a 260K-parameter transformer hold a 512-token context entirely on an ESP32-S3.

At batch size one, decoding a transformer is a memory problem. This project asks what happens when the KV cache moves to PSRAM as int8, the attention scan is mapped onto the Xtensa integer SIMD unit, and every claim is measured on one board with the raw UART captures published alongside the code.

01

Project overview

Problem & objective

Decoding at batch size one is a memory problem. Every generated token reads the entire key/value cache. At 512 context the fp32 cache is 655,360 B, larger than the ESP32-S3's 512 KB of internal SRAM. It has to live in PSRAM, and the attention scan becomes a bandwidth loop over an external memory port.

The obvious move is to store K and V as int8. The obvious move is also a trap: the first int8 build in this project was 19.9% slower than fp32, because dequantising every K value back to fp32 cost more scalar work than the bytes saved. Compression only pays when the scan itself stops dequantising.

This project maps the attention scan onto the 128-bit PIE integer SIMD unit, keeps a 16-position fp32 hot window in SRAM, and measures the result end to end. The cache falls to 245,760 B of payload and scales, the final build reaches 166.6 decode forwards/s, and the raw captures, negative results and analysis scripts are part of the release.

OBJECTIVE

  • Run a complete 260K-parameter decoder on one ESP32-S3.
  • Hold a 512-token context without a host or a network.
  • Make int8 compression a speedup, not just a footprint win.
  • Measure throughput, accuracy and memory on the board.
  • Publish the logs, the rejected ideas and the build config.

WHAT THIS IS NOT

It is not an assistant and not a general-purpose LLM runtime. The checkpoint is Karpathy's 260K TinyStories model: it writes simple children's-story English and is best understood as a reflex-tier runtime. No energy-per-token measurement was made, so no energy claim is made. The MoE work in v1.3.0 is a synthetic prototype with no training and no quality claim.

The cache is 5 layers × 4 KV heads × 512 positions × 8 dimensions. K and V each take 81,920 B as int8, and one fp32 scale per head per position adds 40,960 B each. The attention scan

01 / QUANTISE Q Each query head becomes a 16-byte int8 vector with one zero half.
02 / K DOT One 16-lane EE.VMULAS.S8.ACCX per head per position; four positions per call.
03 / SOFTMAX Table-interpolated exp, normalise and fold the V scale into one pass.
04 / QUANTISE V Folded weights become int8 per head, removing a separate scale pass.
05 / V DOT One SIMD dot over positions per output element; upper four heads run on core 1.

THE CENTRAL RESULT

The naive int8 cache was a regression: 46.52 tok/s against 58.06 tok/s for fp32, a 19.9% loss. The byte saving only becomes a speedup after the K dot, V transpose and folded scale move the scan into the PIE unit. Representation and mapping had to change together.

Seven changes that turned the cache around

  1. Integer K dot. Quantise the query per head and score a position with one 16-lane int8 MAC.
  2. V transpose and folded scale. Store V as [layer][kv_head][dim][pos] and fold the V scale into the softmax weight.
  3. Dual core. Run the upper four heads on a worker task pinned to core 1, with one notification pair per layer.
  4. Scale transpose. Move scales to [layer][head][pos] so a head walks contiguous floats.
  5. softmax_fold. Normalisation, V-scale fold and the folded-weight max in one pass over the scores.
  6. Batched K dot ×4. Load the query once and compute four positions per call.
  7. Inline rounding. Replace lrintf in the quantise loops with an inline integer round.

The ESP32-S3 programs its data cache at startup, so cache size is a build-time choice and every variant is an app-only reflash. config/sdkconfig.64kb and config/sdkconfig.32kb are the full snapshots.

Throughput protocol

  1. Fixed workload. 512-token prompt, 512-token context, batch size one, greedy sampling, same harness in every cell.
  2. Two rates, one run. The 512-sample harness performs 507 decode forwards. Sampled tok/s is 512 divided by elapsed time; decode forwards/s is 507 divided by elapsed time.
  3. Eighteen runs. Six captures of the v1.2.0 firmware, three 512-token runs per capture, with baseline and candidate alternated in one session.
  4. Reflash between sessions. The spread covers flash, boot and allocator placement, not only run-to-run noise.
  5. Two clocks. Wall time from esp_timer_get_time(); core time from cycle counters summed across both cores. They are reported separately because two cores run at once.
  6. Microbenchmarks. Five timings per case, median reported; the empty-call overhead is 5.00 cycles. Each build prints 22 CHECK assertions.

Accuracy protocol

A separate 124-token paragraph is repeated to fill all 512 positions. Logits are dumped at nine depths: 15, 16, 17 (the hot-window boundary), 32 and 64 (the first int8 positions), then 128, 256, 384 and 511. Three paths are compared at the same depths on the same token sequence: fp32 weights with fp32 KV, int8 weights with fp32 KV, and the combined int8 weights with int8 KV.

Top-1 agreement, relative logit RMSE and cosine similarity are reported. Position 15 is a built-in control: it sits inside the fp32 hot window, so the KV-only error there must be exactly zero.

WHAT WAS HELD CONSTANT

Board, clock, prompt, harness, allocator, hot-window size, core assignment and ESP-IDF version. Cache size is part of the experiment, not an implementation detail; comparisons across cache sizes say so explicitly. No number in the release is a single best run.

READING THE NUMBERS HONESTLY

Attention is still 76.7% of the token and the scan is at 85% of the measured port. If attention were free the token would fall to 1.40 ms, but that is not a plan; the remaining levers are fewer bytes per position and a cheaper score path, plus the 23.3% of serial matmul, RoPE and MLP work. The reproducible spread over 18 runs is 0.023%, so the measurement is stable even though the headroom is bounded.

Reproducibility

Build, datasets, verification

The release is built to be re-run, not just read. The firmware, the sdkconfig snapshots, the model hashes and the raw UART captures are all in the repository; the analysis scripts recompute the tables from those logs and fail rather than substitute a default.

Build the research configuration

. $IDF_PATH/export.sh
cd firmware
idf.py set-target esp32s3
cp ../config/sdkconfig.64kb sdkconfig
idf.py fullclean
idf.py build
idf.py -p /dev/ttyACM0 flash monitor

The 32 KB build is the sensitivity baseline, not the headline configuration. The cache size and line size are part of the experiment.

Recompute the results

python3 tools/analyze_bench.py
python3 tools/make_figures.py
python3 tools/micro_report.py

# verify every tracked file
sha256sum -c MANIFEST.sha256

07

Limitations

Scope of the claims

These are constraints on what the numbers mean, not footnotes to hide. The release is deliberately narrow so that every claim is checkable.

ONE BOARD, ONE SILICON REVISION

All measurements come from a single ESP32-S3-CAM, silicon v0.2, 8 MB octal PSRAM. The board vendor and revision were not marked and were not recorded, so they are not claimed. Results may differ on other PSRAM parts or cache configurations.

260K MODEL, 512-TOKEN CONTEXT

The checkpoint writes simple children's-story English. This is a reflex-tier runtime, not an assistant. Nothing here demonstrates quality on reasoning, code, dialogue or long-form tasks.

NO ENERGY MEASUREMENT

Energy per token was not measured. No energy, battery-life or thermal claim is made. Throughput and memory are the only measured axes.

LOGIT ACCURACY, NOT TASK ACCURACY

Top-1 matches the fp32 reference at nine depths, but combined relative logit RMSE reaches 4.564% at position 64. This is a numerical equivalence check, not a downstream benchmark.

THE SCAN IS PORT-LIMITED

51.7 MB/s is about 85% of the measured 60.6 MB/s sequential PSRAM read rate. DMA prefetch and software pipelining were tried and rejected; further gains need fewer bytes per position or a cheaper score path.

v1.3.0 MoE IS SYNTHETIC

The expert sidecar has two synthetic experts, no training and no router learning. The measured costs are real; no quality, routing or load-balancing claim is made. Per-token expert paging from SD is not viable at the measured card rate.

SWITCHING REQUIRES IDENTICAL SHAPES

Runtime model switching in v1.3.0 rejects shape or tokenizer changes. Models with different tensor shapes still require a reboot; the library is a same-shape model selector, not a general runtime.

NO SECURE BOOT OR SIGNED MODELS

The .m8 SHA-256 is an integrity check, not authentication. There is no secure boot, flash encryption or model signing. Do not load blobs from untrusted sources.

Subsequent development — v1.3.0

After the submitted manuscript

NOT EVALUATED IN THE SUBMITTED MANUSCRIPT

Everything in this section is later work. It does not change the evaluated kernels, the measured claims or the accuracy results of v1.2.0. It is included for completeness, not as evidence for the paper.

.M8 MODEL LIBRARY

Prequantized, self-describing blobs with a 4 KiB header, magic M8B1, embedded tokenizer, header CRC32, payload SHA-256 and an on-device sanity fingerprint. The loader probes the header before it stages a byte.

PSRAM CACHE + NVS

Three inactive slots plus the active model, LRU eviction, and model_apply_cached() to swap the active stage without copying the blob again. The last selection is stored in NVS by basename, with a flash-partition fallback.

SYNTHETIC MoE

A MOE1 sidecar stages FFN-only experts in PSRAM and refills a per-layer row range into the existing internal-SRAM arena. Two experts, no training, no router learning, no quality claim.

Forcing the booted model's own FFN reproduces the baseline logits bit for bit (crc 0x4a4a3c07), which validates the sidecar offsets and copy ranges. PSRAM returns to its pre-stage value after the sidecar is unbound.

The card is the reason per-token expert paging was ruled out. On the 1-bit SDMMC bus at 40 MHz, raw sequential reads reach 4.865 MB/s in 64 KiB chunks; FATFS with a 64 KiB buffer reaches 4.31 MB/s on a 1 MiB file, and a mount costs about 82–88 ms. Moving a 34,912 B expert layer per token from SD would cost roughly 7 ms per layer, tens of milliseconds per token before any compute. Staging experts in PSRAM and refilling SRAM at 58–60 MB/s is the viable path.

What did not change: the v1.2.0 kernels, the int8 KV layout, the accuracy results and the TECS claims. v1.3.0 adds a runtime around the frozen core.
